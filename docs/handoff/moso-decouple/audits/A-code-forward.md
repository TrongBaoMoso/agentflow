### 2b. recruit → packs "Recruit API" (`/api/recruit/v1/*`, packs `RecruitAPI.java`, `@Api(name="recruit")`)

Most writes are queued in the outbox `packs_writeback_outbox` and delivered by a 5-minute relay tick. packs answers HTTP 200 even for refusals.

## 3. Narrative by business flow

**1. Collecting LOs (Hot and Cold).** Recruit cannot create a candidate on its own in production: `recruit.features.native-candidate-create` defaults to false and is not set in the staging or prod values (A-086 below). Every Hot lead arrives by **the MOSO push** (A-001), from an LF-site form (Register-LO, webinar sign-up, Refer-a-LO, FB ads), through packs `LORecruiting`, a TypeWatcher, a GAE task queue and `SendLORecruitingToRecruitOp`. The **Cold** pool is the **MOSO migration import** (A-004, with the ownerMap of old MOSO recruiter keys). Suppression comes from MOSO's blacklist and opt-out tables (A-006). The only other channel is Modex CSV (not MOSO). Leads created that way have no `legacy_key` and so can never be invited (A-016).

**2. Loans counts / production / experience.** All loan figures come from MOSO's row (A-007): `closed_loans_since_2021`, 12-month units and volume. They drive "Loans since", the production band and sort, offer auto-approve, the program "verified loans" check and the D302 experience level. The experience level is written back to MOSO for the commission plan (A-031, dark).

**3. Licensing / NMLS.** NMLS id/status, sponsor states and sponsorship dates come from MOSO (A-008). They seed `sponsorships` as `LEGACY_IMPORT` and feed the FROM_MOSO bucket. Profile licensed/sponsor states are written back (A-020). Post-joined licences come from user-service and HR (A-076, A-080, TERA). NMLS links point to nmlsconsumeraccess.org (not MOSO).

**4. Today / Hot SLA / call & log result.** Today reads the MOSO-mirrored onboarding status (A-011). Touch clocks come from omni Pub/Sub (A-049, A-048). Hot idle release asks omni for outbound messages before releasing a lead (A-046). A call is a `zoomphonecall:` deep link (Zoom, not MOSO), mirrored into omni (A-044). Meet 1-1s are mirrored into omni (A-045).

**5. Webinar.** The dropdown comes from packs WebPlus `getNextWebinars` (A-034). Registration goes through packs `/candidate/registerWebinar`, and MOSO sends the confirmation (A-023). Attendance comes back in the push (A-009).

**6. Offer / invite.** An offer needs `legacy_key` (A-016). Once SENT, the invite email is sent by MOSO via `/candidate/invite` (A-021), as the acting MOSO Admin (A-019). Signed/paid state comes back by push (A-010) and by the 20-minute pull sweep (A-032). The Exceptions desk exists for mismatches. LF/LO homepage's pay-gate asks recruit `register-status` with the MOSO key (A-067).

**7. Onboarding hand-off / contract / e-sign.** The specialist is set in MOSO (A-022). The 1-1 done goes to MOSO, which sends the welcome email and runs agreement flow V2 (A-025). Agreement status is a MOSO dry run (A-026), and **sending the e-sign (Inkless) agreement is done entirely by MOSO** (A-027). Reminder emails before the 1-1 are sent by MOSO (A-028; prod flag true). HR hand-off goes to ai-hr-be (A-080, TERA).

**8. Emails / SMS / notifications.**
- Sent by **packs/MOSO**: invite (A-021), webinar confirmation (A-023), welcome/onboarding (A-025), agreement (A-027), 1-1 reminders (A-028).
- Sent by **moso-notifier** (SendGrid) from recruit's Pub/Sub events: nurture drip, scheduled Send info (A-037). Delivery status comes back on STATUS_MAIL (A-040). The cross-app bell goes through moso-notifier IN_APP (A-039).
- Recruiter's **manual** SMS/email to the LO: entirely in **omni** (FE omni-react A-054; replies A-048; sent A-049; reply-to address A-047). SMS sender identity goes through omni/zoom-go, using an old LOS key (A-053).
- Recruit-be has **no** SMTP, SendGrid or Twilio client of its own (§4).

**9. Referral / ambassador / Headhunter.** Referral markers come in the push (A-013). "My referrals" and admin referrals plus bonus Check state come live from packs (A-029, A-030). Headhunter attribution uses packs origin stamps (A-012). Program roles follow the moso-aid roster (A-035), decoded with MOSO app id/namespace pins (A-036).

**10. Login / users / roles.** Login is TERA central (account portal + auth-svc + gateway-injected `X-User-ID`, A-073). It is not MOSO. Roles are local RBAC (A-075). But **any action that reaches MOSO requires the person to be an active MOSO Admin with RECRUITING** (A-019). In practice that is a second, MOSO-side user/role requirement for every recruiter and onboarding specialist.

**11. Omni timeline / conversation.** This is all omni-service (A-042 to A-054), both directions, plus Redis (A-051).

**12. Infra.** Both apps run in **MOSO's GKE clusters** (`moso-gke`, `moso-kube`), in **MOSO's GCP projects** (`lender-rate`, `lenderrate-master`), pull from MOSO's registry (`moso-svc-repo`), and use Pub/Sub topics in those projects (A-055 to A-065).
