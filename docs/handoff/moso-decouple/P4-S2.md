## What changed

The page is `/register-loan-officer` (and `-v1`, `-v2`, plus `/recruit/<slug>`, which share `useRegisterLoanOfficerFlow`).

**`?t=<token>` (new).** Every read and write goes to recruit-be (`/public/api/v1/onboarding`, D368 + D375). They go through a new server route, `POST /webplus-api/onboarding/<action>` (`src/app/webplus-api/onboarding/[action]/route.ts` → `src/apis/onboardingPortalProxy.ts`).

| Action | What it does |
|---|---|
| `profile` | `GET /profile` |
| `save` | `PUT /profile` |
| `fee-config` | `GET /fee-config`. Called with the token, so the answer also carries `paypal_custom_id` |
| `page-texts` | `GET /page-texts?paid_startup_fee=` |
| `fee-paypal` | `POST /fee/paypal {order_id}` |

- **Where the secrets go.** The route adds the server-only `x-api-key` and moves the token into `x-onboarding-token`, so the token never appears in a URL. It also passes `x-client-ip` for recruit-be's rate limit.
- **What the browser sees.** Upstream error bodies are never passed on: 401/403/5xx become 502, and only the action and the status are logged.
- **Why `/webplus-api/` and not `app/api/`.** The middleware has no matcher, so `/api/*` would go through i18n routing. The public hosts also send `/webplus-api/*` POSTs to a legacy 405 backend. The browser therefore calls the Cloud Run host (`NEXT_PUBLIC_ASSET_URL`) with a text/plain POST, the same as `recruit-intake` (#2699).
- **Same page, new source.** The page uses the same UI, steps, gates and tracking ids. Recruit's profile already uses packs' field names, so `toRegisterFormValues` is reused as is.
- **Fee.** The fee config comes from Recruit.
  - A missing or bad config fails closed, so the page shows "payment unavailable". It never falls back to MOSO's config.
  - The PayPal order carries `purchase_units[0].custom_id = paypal_custom_id` (D375 binding).
  - The SDK is reloaded with Recruit's client id if it differs from MOSO's, and the button is held back until it has loaded (`PortalPaypalGate`).
  - The captured order goes to `fee-paypal`: PAID sets paid, WAIVED sets waived. It is retried once on a 5xx or 429.
  - Anything else (REJECTED, an error) shows the page's existing error modal (`Error.something_went_wrong`).
- **Page texts.** Recruit's `onboarding_process` and `startup_fee_desc` replace the MOSO ones when they load. Otherwise the server-rendered MOSO text stays. recruit-be cleans this HTML against a jsoup allowlist before serving it.
- **Identity fields stay read-only.** A token registration is treated as a stored one: the fields that are read-only for a `?key=` stay read-only, and the "new applicant" prefills are skipped. The marker is the form-only field `is_portal_registration`, which is never sent anywhere.
- **What a token save skips.** It never creates a lead: no recruit-intake dual-post, no lead-origin stamp, no `?key=` redirect. It also never asks packs for a signing link.
- **Clean-up on leaving the page.** The Recruit link state is cleared and MOSO's PayPal config is put back.

**`?key=` (packs): unchanged.**
- The same calls are made in the same order. The load body was moved into `applyLoadedRecord` without changes.
- `hasRegistrationRef` is true for a key exactly when the old `get('key')` check was.
- If a URL carries both `t` and `key`, `t` wins.

**No lo-homepage twin** (§5 Q8 is still open).

## Open questions

1. **E-sign on `?t=`.** S4/S5 are not built, so the page never asks packs for a signing link on a token registration.
   - The "Review & sign" step shows its existing card, but with no link, so the button does nothing. This is the same as today's packs behaviour when MOSO has not built the envelope yet.
   - There is no existing "coming soon" copy for this, so none was invented.
   - Should S5 land before any real LO gets a `?t=` link, or should the sign step say something?
2. **Payment not recorded.** If a PayPal capture is REJECTED, or still fails after one retry, the LO sees the generic "something went wrong" modal. The packs path shows nothing at all.
   - Is a dedicated message wanted ("we received your payment, our team will confirm", plus the order id)? That needs copy and i18n in 5 locales.
3. **Done text.** `done_thanks` is loaded by recruit-be but not used. The page does not use MOSO's `lo_recruiting_done_thanks` today either: the thank-you page has static i18n copy.
4. **Link lifetime and a dead link.** A dead or rotated token shows the existing "Key is not exist" modal, the same as a bad `?key=`. §5 Q1 (lifetime, resend) is still Bao's call.
5. **lo-homepage.** `/register-loan-officer` there has no adapter (§5 Q8, for Khải).
6. **Referrer leak.** The `t` token stays in the address bar and can reach third-party scripts (Maps, reCAPTCHA, PayPal) as a Referer, exactly like `?key=` does today.
   - Possible fix: a `Referrer-Policy: strict-origin` for this page. It is a site-wide header decision, so it is not in this PR.
7. **Pre-existing failure on master.** `src/shared/utils/__tests__/leadOriginCallers.test.ts` fails on master. It lists `recruit-intake/sanitizeLead.ts` and `recruitIntake.ts` from #2694, and this PR does not touch them.

## Review

An independent code review (a code-reviewer agent given the diff only) found 0 CRITICAL and 3 HIGH. All 3 HIGH are fixed:
1. Identity fields were editable on `?t=`.
2. A payment could be captured but not recorded, silently.
3. The PayPal client-id reset could race the button.

Of the MEDIUM findings:
- **Fixed:** non-object 200 bodies now answer 502, and MOSO's PayPal config is restored on unmount.
- **Not changed:** server-side sanitising of page texts, because recruit-be already cleans them with a jsoup allowlist.

The LOW findings (Referer, CORS `*`, the XFF topology) are noted in the open questions; they behave the same as `recruit-intake` and `?key=` today.
