## 5. Why the OB is assigned only at SENT

**(a) What the code does**
- The only call site is `OfferServiceImpl.java:597` (`assignIfAbsent`, inside `transitionToSent`), and the interface says so (`BE/onboarding/service/OnboardingSpecialistAssignmentService.java:9-14`).
- Round-robin is least-open-`ONB_PREMEETING`, behind a global advisory lock (`OnboardingSpecialistAssignmentServiceImpl.java:30-50,101-139`).
- The pick is write-once (`:106-109`).
- **A PENDING_APPROVAL offer has no OB**, unless the candidate kept one from an earlier SENT offer or a manual "Assign" in Department work.

**(b) Why:** D137 (DEC:191, agentflow-5ek0, closed): "onboarding specialist assigned at offer SENT".
- The specialist travels on the MOSO INVITE payload and is never reassigned. Packs' `onboarding_specialist` stops being idempotent past `pre_onboarding_done`.
- Assigning at request would burn the write-once slot on offers a manager may decline.
- It would also skew the round-robin, which counts `ONB_PREMEETING` items. Those items are created at SENT (`ON_OFFER_SENT` trigger).
- R21 (Option A) was rejected.
- With the hand-off, SENT is also the OB's cue (D207 (4)).

**(c) Verdict:** by design.

**(d) Optional:** the approval row could show "Will be handed to the next onboarding specialist" for context. No BE change is needed.

## 11. B9: "manager declines an offer the loan officer already paid"

**(a) What the code does**
- The BE allows decline from PENDING_APPROVAL, APPROVED and SENT (`OfferServiceImpl.java:98-99,415-433`).
- **The only Decline button in the FE** is in `ApprovalQueueSection`, which lists PENDING_APPROVAL only (`OfferServiceImpl.java:696-697`). It is gated on OFFER_APPROVE (`ApprovalQueueSection/index.tsx:68,105`). grep `useDeclineOffer` finds only that component.
- **A SENT offer cannot be declined in the UI anywhere.**
- The "Fee already paid" chip (`:221-225`) and `refund_warning` (`:328-333`, `approvals.json:28`) are reachable only for a pending offer whose `fee_status = PAID`.

How a pending offer can already be PAID:
- (i) **MOSO reconcile.** A MOSO push reconciles the fee onto the open offer, and PENDING_APPROVAL is in the open set (`BE/moso/service/impl/MosoRowUpsertServiceImpl.java:104-106,1107-1115` → `reconcileFromLegacy`, `OfferServiceImpl.java:927`). If the MOSO row has `paid_startup_fee=true` (the loan officer paid on a legacy/earlier invite link), the pending recruit offer becomes PAID.
- (ii) **API.** `POST /offers/{id}/fee-paid` (OFFER_APPROVE) checks only `assertFeePending`, not the offer status (`OfferServiceImpl.java:635-647,1041-1045`). It marks a PENDING_APPROVAL offer as paid.

**(b) Why:** Brian 05/08, "an LO must never pay before being approved" (class comment `ApprovalQueueSection:39`). The warning was built for legacy rows that were already paid.

**(c) Verdict:** in the new flow B9 cannot be reached through normal UI. It is testable only via the legacy MOSO state or the API. Side finding: `markFeePaid` accepting a non-SENT offer is a latent hole. It should require status SENT/SIGNED.

**Exact steps (staging)**
1. As a recruiter, request an offer for a MOSO-linked loan officer with a waive, or with a figure below the minimum, so it lands in PENDING_APPROVAL.
2. Make it PAID, either way:
   - (API) as a manager: `POST /recruit-svc/api/v1/offers/{offerId}/fee-paid`, or
   - (MOSO) set `paid_startup_fee=true` on the loan officer's MOSO row and wait for or trigger the push.
3. As a manager, open Today → "Waiting on your decision". The row shows the red chip "Fee already paid".
4. Click Decline. The modal shows "This loan officer already paid the fee. Declining means the fee must be refunded — the reason will record it."
5. Enter a reason of at least the minimum length, then click Decline. The offer becomes DECLINED and the ledger keeps the reason.

**(d) Fix**
- BE: in `markFeePaid`, require `status ∈ {SENT, SIGNED}`.
- Product: decide whether a SENT/paid offer needs a "Withdraw invite" action, in the drawer Attention block, for managers. If yes, reuse the decline modal with the refund warning.

For a non-program offer with no collected stamp it returns `null` at `:148-150`. **Self-approval is allowed.** The ledger shows REQUESTED (manager), then APPROVED (same manager), then SENT.
- `approvals.json:40` `refusal_SELF_REQUEST` appears only for program-role requesters.

**(b) Policy:** D194 (2) (DEC:54) blocks self-approval only for program-role requesters. It explicitly says "A manager or admin who requests on a program-collected lead MAY approve it themselves … a 403 there would deadlock a team with one approver". D201 (DEC:48) keeps "self-approval stays blocked" for program members only. **There is no general separation-of-duties rule**, so a manager self-approving a plain offer is allowed by policy.

**(c) Verdict:** by design. The two-step flow is friction, not a guard.

**(d) Proposal**
- BE: `RequestOfferRequest.approveNow` (boolean). In `OfferServiceImpl#request`, if it is set and the actor holds OFFER_APPROVE and `programRefusal(...) == null`:
  - after the REQUESTED row, call the same body as `approve(saved.getId(), keepFee=!waiveFee, actorId)` in the same transaction.
  - This gives an APPROVED ledger row with the manager as actor, reason "Approved by requester" plus the D64 reasons that held it, so the bypass stays auditable. SENT follows.
  - Otherwise refuse with 403, or fall back to PENDING.
- FE `InviteModal`: when `useCan('OFFER_APPROVE')`, not a program member, and `knownReview`:
  - primary button `submit_approve_handoff` "Approve & hand to onboarding" (or "Approve & send invite" when the flag is off)
  - secondary "Request approval from another manager".
- Risk: the waive is the money decision. Consider requiring a second approver whenever `waive_fee` is set (or behind a setting `offer.self_approve_waive_allowed=false`), and list self-approved offers in Audit/Reports. Bao needs to confirm, since no decision exists today.
