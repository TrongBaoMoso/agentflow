## Q4. What "Department work" is for, and how it differs from Exceptions and Today

| Screen | Whose screen | What it lists | Evidence |
|---|---|---|---|
| **Today** | Each person's own | Rows assigned to *me*. For an Onboarding specialist this is the "Your onboarding" section: only candidates whose `onboarding_specialist_id = me`, at S5/S6, ACTIVE, with the 1-1 not finished. | BE `dashboard/OnboardingTodayReader.java:67-80` (`where c.onboardingSpecialistId = :actor`) |
| **Exceptions** | Recruiting MANAGER | A lens on **Kho HOT**: leads past their first-touch SLA or unclaimed too long. | **Department work** (`/work`) | A whole **department** (in the UI: Onboarding and Accounting) | Every **open checklist item** that belongs to the chosen department, for **every** candidate, oldest due date first. For ONBOARDING it also includes DONE 1-1 rows whose MOSO write-back is stuck. Why it is unclear: the name says "department" but the rows are tasks, and nothing on the page says whose task each one is. On staging the ONBOARDING queue holds about 500+ open items (the cap is 500). Only 16 of them are 1-1 rows that name a specialist, and the other 499 have `assignee_id = NONE`. So for an Onboarding specialist, "Department work" means "everything Onboarding as a team owes". "Today" means "my own 1-1s". The design reason is in V097:73-83 and in the `ChecklistFacadeImpl` javadoc (`:30-37`): *"Onboarding described chasing HR and Licensing by e-mail because their progress was invisible — everyone sees everything, everyone writes only their own."*

### Role × screen × capability for Department work

The FE menu entry requires `permission: 'CHECKLIST_READ'` **and** `roles: DEPT_WORK = ['MANAGER','ONBOARDING','ACCOUNTING']` (`recruitNav.tsx:117,204-210`). The URL guard reads **only** the permission (`PermissionRouteGuard.tsx:40-45` + `routeGuard.ts` `findRequiredPermission` returns `match?.permission`), so the role list hides the menu entry but does not lock the URL. The tabs show only ONBOARDING and ACCOUNTING (`apis/recruit/checklist.api.ts:22` `QUEUE_DEPARTMENTS`), but the API accepts all five departments.

| Role | (a) Sees "Department work" in the menu | (b) Opens `/work` by URL and gets data | (c) Departments whose rows it can read | (d) What it can do on rows |
|---|---|---|---|---|
| RECRUITER | No | **Yes**: page renders, API returns 200 | All (ONB, ACC, HR, LIC via API) | Nothing. No MANAGE permission, so Done/Block/N/A are hidden and PATCH returns 403. |
| LO_SUPPORT / OFFICER_RECRUITER | No | **Yes** | All | Nothing |
| MANAGER | Yes | Yes | All | **Assign specialist** only, and only on a row with no specialist ("Needs owner", `WorkQueueClient/index.tsx:420`). The BE also allows *changing* the specialist on any candidate. A manager **cannot** mark Done/Block/N/A (no CHECKLIST_ITEM_MANAGE_*). |
| ONBOARDING | Yes | Yes | All | On **every** ONBOARDING row: Done / Block / N/A / Reopen, Send again (resend), Assign/change specialist. **Schedule 1-1 only on its own rows** (assignee check). |
| ACCOUNTING | Yes | Yes | All | Done / Block / N/A on ACCOUNTING rows only |
| HR | No (`ROLES_WITHOUT_NAV_AUDIENCE`, `recruitNav.tsx:104`) | Yes by URL | All | HR rows, through the API only (there is no HR tab) |
| LICENSING | No | Yes by URL | All | LICENSING rows, through the API only |
| HEADHUNTER / TEAM_LEAD | No | The page opens (they hold CHECKLIST_READ), but the queue call gets **403** from `ScopedRouteAllowlist`, so they see the "You cannot see department work" empty state | None | None |
| ADMIN (`*`) | Yes | Yes | All | Everything, including Schedule if the admin is the assignee |

Gates in code:
- Read: `ChecklistFacadeImpl.java:96-100,113-115` (`require(CHECKLIST_READ)`, the same for every department).
- Write: `:124-131` `demandManage(item.getDepartment())`, which checks the permission only and has **no assignee or specialist check**.
- Schedule: `:254-266`, which requires both an assignee and `item.assigneeId == actor`.
- Resend: `onboarding/controller/OnboardingMeetingController.java:30-38`, permission only.
- Assign: `onboarding/controller/OnboardingSpecialistController.java:51-65`, permission only.

**Can a RECRUITER read OB's queue?** **Yes.** In code: V109:27-29 grants CHECKLIST_READ, and the queue gate is that one flat permission. On staging: as `bao.trinh+recruiter@`, `GET /checklist/departments/ONBOARDING/queue?limit=500` returned **200 with 500 rows**, and `/ACCOUNTING/queue` returned 200. V109's stated reason was the drawer's checklist panel (`:8-12`), and the department queue came along with it. Stale comment: `recruitNav.tsx:202-203` still says "recruiters do not hold it [CHECKLIST_READ]". That stopped being true at V109.

**Is there an "Onboarding lead / OB manager" role?** **No.** The 11 seeded roles are the ones above (`recruitNav.tsx:89-101`). `TEAM_LEAD` is the Loan Officer Recruiter Program (headhunter) team lead (V191:30), not an Onboarding lead.
- Who assigns: the system assigns automatically. Round robin picks the least-loaded ONBOARDING grant holder when the offer is SENT (DECISIONS **D137**, line 191, `OnboardingSpecialistAssignmentServiceImpl#leastLoaded`).
- Manual assign/change is `ONBOARDING_SPECIALIST_ASSIGN`, which is held by **every ONBOARDING specialist and by the recruiting MANAGER**. V142:21-25 explains it: "ONBOARDING (does the work day to day) and MANAGER (the escalation path when a specialist is unavailable)".
- So the recruiting manager (Victoria) is the escalation path, and any specialist can reassign a peer's Loan Officer.
- D79 (line 134) says MANAGER has global scope in V1 because "there is exactly one real manager". The question "which manager per department" is postponed until a second manager exists.

### Act: **YES** for almost everything except Schedule 1-1

Write gates are checked in code only. No POST/PUT/PATCH was sent.

| Action on another specialist's Loan Officer | Allowed? | Gate |
|---|---|---|
| Mark 1-1 Done / Block / N/A / Reopen (PATCH `/checklist-items/{id}`) | **Yes**, any ONBOARDING holder | `ChecklistFacadeImpl.java:103-110,124-131`: permission only, no assignee check. FE `canManage` is permission only (`WorkQueueClient/index.tsx:169`), so the buttons show on every row (`:533-596`). |
| Send again (resend the MOSO write-back) | **Yes** | `OnboardingMeetingController.java:30-38` |
| Send to HR | **Yes** | `HrHandoffController.java:30-33`: `require(CANDIDATE_HR_HANDOFF)` only. FE `SendToHr/index.tsx:60` uses `useCan` only. |
| Reassign the specialist (including to self) | **Yes** in the BE. The FE only offers it on "Needs owner" rows. | `OnboardingSpecialistController.java:51-65`; FE `index.tsx:420` |
| Send agreement, edit profile (CANDIDATE_UPDATE), confirm legal name | **Yes** | V158, V106 and V147 grants, all flat |
| **Schedule / clear the 1-1 slot** | **No**, assignee only | BE `ChecklistFacadeImpl.java:254-266`; FE `workQueue.ts:221-226`. D151 (DECISIONS line 212): "caller = the item's own assignee … never a manager override". The way around it is to reassign the specialist first, which anyone in ONBOARDING can do. |

**Why it is like this.** DECISIONS **D78** (line 133) chose the opposite: *"Onboarding = narrow seat (GHẾ HẸP)… their work is their own items, not the pipeline — a full seat only creates noise"*. Its visibility rule was D76's "open item or relationship" row scope. That row scope was **never built**: `rbac_roles.row_scope` was a dead column until V191, and it now restricts only HEADHUNTER/TEAM_LEAD. V003 gave ONBOARDING flat CANDIDATE_READ instead. So the current "everyone sees everything" was not a deliberate onboarding decision. It comes from the flat-read choice made for cross-department visibility (V097, V109).

## Options to make Department work clearer

**Option A: Rename and split by audience. Smallest change, FE plus one BE parameter.**
- Rename "Department work" to **"Onboarding team queue"** (and "Accounting queue"). Add an **"Assigned to"** column and a **Mine / Everyone / Needs owner** filter (URL `?who=`), defaulting to *Mine* for ONBOARDING.
- Hide the Accounting tab from ONBOARDING and the Onboarding tab from ACCOUNTING. Fix the URL guard so `/work` also honours `roles` (or add `permission: 'CHECKLIST_ITEM_MANAGE_*'` via `anyOf`). Recruiters, HR and Licensing then get redirected instead of seeing a queue they cannot act on. Remove the stale comment at `recruitNav.tsx:202-203`.
- BE: optional `?assignee=me|none|any` on `GET /checklist/departments/{d}/queue`. The filter goes in `ChecklistItemServiceImpl#openSlice` (for ONB_PREMEETING by `assignee_id` / `candidates.onboarding_specialist_id`).
- Reads stay flat, so this changes no security behaviour.

**Option B: Restrict reads to your own department plus your own Loan Officers. BE permission change.**
- BE: `queueByDepartment` / `listOpenByDepartment` require `CHECKLIST_ITEM_MANAGE_<dept>` (or a new `CHECKLIST_QUEUE_READ_<dept>`) instead of the flat CHECKLIST_READ. The drawer's `GET /candidates/{id}/checklist-items` keeps CHECKLIST_READ, which preserves V097's "see HR/Licensing progress" need.
- Writes on ONB_PREMEETING items, plus Send to HR, resend and agreement, add "assignee == actor OR actor holds ONBOARDING_LEAD". This is the same shape as the existing Schedule check at `ChecklistFacadeImpl:254-266`.
- Result: recruiters lose `/work` (they never acted there), and a specialist can no longer close a peer's 1-1.
- FE: hide the actions when `row.onboarding_meeting.specialist !== me`. Flyway migration only for the new permission.

**Option C: Add an "Onboarding lead" role and an Onboarding-manager view. Larger change, closest to D78.**
- New role `ONBOARDING_LEAD`: ONBOARDING permissions plus `ONBOARDING_SPECIALIST_ASSIGN` plus the cross-specialist write override.
- Remove `ONBOARDING_SPECIALIST_ASSIGN` from plain ONBOARDING (reverses part of V142). Decide whether MANAGER keeps it as the escalation path.
- Give plain ONBOARDING a `row_scope` `{"candidates":"ONBOARDING_SELF"}`: reads limited to `onboarding_specialist_id = me` (plus D76's open-item rule), enforced by `CandidateRowScopeService` / `CandidateRowScopeInterceptor`, the same mechanism as HEADHUNTER. The lead role lifts the scope.
- FE: a new **"Onboarding team"** page for the lead (Exceptions-style: Needs owner, overdue 1-1s by specialist, stuck write-backs, reassign), with `/work` becoming each specialist's own list. A new `NAV_AUDIENCE` entry and an update to `SEEDED_ROLE_CODES` are needed.
- Needs Bao to decide who holds the lead role, and a new DECISIONS entry that supersedes D78/V142.

My recommendation: do A now (no access change, removes the confusion). Then B or C depending on Bao's answer to: "should specialists be able to close or see each other's Loan Officers?"
